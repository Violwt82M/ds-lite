## 二、服务端硬规则（实测，2026-11-16，别再用旧的错误结论）

| 规则 | 数值 |
|---|---|
| 上下文窗口 | 1,048,576 token（deepseek-flash / deepseek-v4-pro 相同） |
| 输出上限 | 393,216 token |
| 计费公式 | **输入 + 请求里的 max_tokens ≤ 1,048,576**（实测 104.6万+8 通过、105万+8 被拒） |
| 标准模式 | 能发到 ~104.8 万 token（实测 60 万字 = 16.7 万 token 正常） |
| **扩展模式** | **输入上限 32768 token（约 5.3 万字），超了直接 400** |
| 文档超限 | **服务端不会替你截断**，直接 400（实测 145 万 token 的 6.4MB txt） |
| `count_tokens` | 存在但**不统计 document 块**（永远返回几十），不能用来数文件 |
| 中文折算 | 0.59~0.70 token/字符；文件约 4.0~4.7 字节/token |

### 什么会触发「扩展模式」（任何一条都算）

1. `title: { enabled: true }` —— **每个新会话的第一条消息都会带**
2. `tools` 含 `deepseek_read_url`
3. `tools` 含 `deepseek_web_search`（智能搜索开关）
4. `safety_check.level = high`（内容审查 = 严格）

**结论**：只要请求体里出现任一扩展字段，输入上限就从 100 万掉到 3.2 万。
这就是「只能发 5 万字」的真正原因，也是交接报告里那条「32768 是服务端静态上限」错误结论的来源。

### 三之二、文档读取（0.9.28.6 重写，用实测数据说话）

| 事实 | 数值 |
|---|---|
| 中文散文 token 折算 | **0.605 token/字**（50,061 字 → 30,269 token，实测） |
| 纯 ASCII | 4.5 字节/token（50,000 字符 → 11,162 token） |
| 服务端能否认 GBK | **能**。同一份内容存成 UTF-8 / GBK，服务端都是 30,268~30,269 token |
| JS 按 UTF-8 硬解 GBK | **70.5% 的字节变成 U+FFFD**（模型看到一片乱码） |
| 单份文档预算 | 35 万 token ≈ **53.8 万字**（350,000 ÷ 0.65）；切点在段落/句末，safeSlice 防切半 emoji |

**旧实现的两个错**：

1. 拿 file.size（字节）和 DOCUMENT_CHAR_BUDGET（字符）比较 —— 单位不同，等于没判；
2. 中文 1.3 MB 只有约 45 万字 < 50 万字，于是判定「在预算内」**原样上传** → 服务端 400。

**旧估算的错**：DOCUMENT_BYTES_PER_TOKEN = 4。GBK 中文小说约 2 字节/字、0.6 token/字 ≈ **3.3 字节/token**，UTF-8 约 5 字节/token，一律按 4 猜会低估。

**现在的做法**：解码（严格 UTF-8 → GB18030 兜底）→ 估算 token → 超预算就在段落边界切 → 卡片显示「模型仅阅读了 52%」，发送时再弹「前 52%（约 34 万字 / 共 65 万字）」。
实测：GBK 2.09 MB / 105 万字 → 切到 54.2 万字（52%），本地估 349,978，服务端 count_tokens 359,382（误差 2.6%，偏低估）。

## 七、坑（越踩越深的那几个）

1. **任何扩展字段都会把输入上限砍到 3.2 万**。加请求字段前先问：它会不会进扩展模式？
2. **JS 字符串按 UTF-16 计长度**。按字符截断会切出半个 emoji，服务端 JSON 解析直接 400。切一律走 `safeText`。
3. **服务端不会帮你兜底**：超限就 400，截断只能客户端做，做完必须告诉用户读了百分之多少。
4. **附件按体积估 token**（4 字节/token），界面显示与实际可能差 15%。
5. **改 CSS 后必须无头截图看**（0.9.25 白屏、0.9.26 荣耀白屏都是只看代码看不出来的）。
6. **i18n 必须成对**：`zh.ts` 是类型源，`en.ts` 少 key 直接 tsc 报错；字符串里别用英文撇号。
7. **git 必须带代理覆盖**：`-c http.https://github.com.proxy=`，否则本机 socks5h 配置会让凭据管理器报错。

## 八、0.9.38「越聊越短」实验结论（2026-11-18，决定：日志整理保持现状）

用户反馈长对话后回答越来越短。用真实 API（deepseek-flash，每组 3 次取均值）做了三组对照：

| 实验 | 结果 |
|---|---|
| 有 / 无【前情提要】段（2 轮对话） | 68 字 vs 64 字——**提要文案本身不影响长度** |
| 0.9.38 现版提要 vs 旧版「请据此保持前后一致」 | 68 vs 52——**旧版更短，回滚无意义** |
| 历史里助手回答换成短版 / 长版（语义相同） | **28 字 vs 127 字（4.5 倍）** |
| 6 轮全原文 vs 前 4 轮折叠成笔记 | 78 vs 67（折叠后短约 14%） |

**机制**：模型会拟合最近几轮助手回答的长度。整理把较长的原文折叠走后，上下文里的长文样本变少 → 输出变短 → 更短的回答又成为新样本（棘轮效应，向下不可逆）。不是「提要文字污染风格」。

**已否决的改法**：
- 回滚整理预设：旧文案实测更短，且会把「反复围绕旧情节」带回来；
- 加「文风锚点」（固定保留最早几段长回答做 few-shot）：**之前就是这么做的，导致 OOC，用户明确否决**；
- 提高 `MEMORY_KEEP_TOKENS`（24k → 32k+）：用户决定「就现在这样」，暂不改。

以后有人再提「越聊越短」，先看这节，别重测、别再提锚点。

## 十、0.9.50 beta4：公式渲染改成官方同款链（KaTeX → MicroTeX）

**结论先行**：官方的公式渲染是**双引擎**，和此前「客户端画气泡」的结论（第九节）不是同一件事：

1. 官方前端主包里的 KaTeX 版本是 **0.16.22**（和 ds-lite 完全一样），渲染参数也一样：`renderToString({ throwOnError: true, strict: false, displayMode: !isInline })`。
2. KaTeX 抛错后，官方只做两条小修复（`\text{…·…}` 拆成 `\text{…}\cdot\text{…}`；`\big{…}` 去掉多余花括号），还失败就**降级到 MicroTeX**：
   ```js
   const { svg, baseline, error } = microtex.render(latex, { textSize: 20, color: 0xff000000, isInline, strict: true })
   svg = svg.replace(/(fill|stroke)="rgb\(0,0,0\)"/g, '$1="currentColor"')   // 深色主题靠它
   行内对齐：style.verticalAlign = (svg 高度 - baseline + 1) + 'px'
   ```
   展示块：`<span class="ds-markdown-math ds-markdown-math-svg ds-markdown-math-display">` + SVG；CSS `max-width:100%; height:auto`，超宽自己横向滚。
3. MicroTeX（`@deepseek/latex-wasm` → `microtex-wasm.c7b36d1fce.wasm`，2.97MB）是 C++ 的 TeX 排版引擎编译成 wasm，输出 SVG；中文走 SVG `<text>` + 系统字体，字宽用 canvas 回调量。

**为什么「我们的美化包公式和官方不像」**：引擎不同。
- 官方：KaTeX 排不了 → MicroTeX 排，形状由 MicroTeX 的 box 模型决定（`\colorbox` 内边距大、三角相对正文更小、负 `\hspace` 会把色块压到三角上）。
- 我们（beta3 及以前）：KaTeX 排不了 → `prepareLatex` 补数学岛后**继续用 KaTeX 排**，于是 `\raisebox{0.3cm}` 真抬、`\hspace{-0.6cm}` 真负间距 → 三角跑到色块上沿、色块被拖过去盖住三角。
- 不要针对某一条公式调参数：要像官方就得接同一条链。
- 另外：用户截图里那条「官方效果」是模型改写过的公式，不是原始模板；同一引擎按原始模板排会把三角盖住。以后对比一律「同一串输入 + 同一引擎」。

**落地**：
- `public/microtex/microtex-loader.js`：官方异步 chunk 55223（60KB，含 emscripten 胶水层）包成普通脚本，挂出 `window.__dsMicrotexFactory`；换资源重跑 `scripts/gen-microtex-loader.mjs` 即可。
- `public/microtex/microtex.wasm`：官方那份原样。
- `src/services/markdown/microtex.ts`：按需加载（第一次遇到 KaTeX 排不了的公式才拉 wasm）+ 结果缓存（上限 256 条）；自己 fetch 成 ArrayBuffer 再以 `wasmBinary` 交给 emscripten，避开 Capacitor 本地服务器 `.wasm` MIME 不标准导致 instantiateStreaming 失败。
- `MathFormula.tsx` 顺序：**KaTeX → MicroTeX SVG → prepareLatex 兼容层**。最后这档是保险：离线、`file://`、资源缺失时仍按旧方式渲染，不会因为公式崩掉聊天。
- 体积：wasm 不在 Service Worker 预缓存白名单里，首次用到才下载（网页版）；APK 内是随包静态资源。

## 十一、0.9.50 beta4：DSML 标记泄漏 / 无法继续聊天 / 会话消失

**用户反馈**：多次「重新生成」后回答正文里出现 `</||DSML||parameter>`、`</||DSML||invoke>`、`</||DSML||calls>`（竖线可能是全角 `｜`）；之后无法继续聊天；重启 APP 后该会话记录消失。

**根因（三条，互相独立）**：
1. **泄漏**：`parseEvent.ts` 的 `text_delta` 原样透传，`reply.ts` 直接 `text + delta.text` 拼接，全仓库没有任何特殊 token/DSML 过滤；mdast 把 `</||DSML||parameter>` 当普通段落文本渲染，内联 HTML 白名单又只认 `[a-zA-Z][\w-]*` 标签名，`|` 不匹配所以连"丢弃"都不触发。重新生成 = 每次都重新跑流，服务端偶发下发协议标记时每次都被存下来。
2. **没法继续聊**：脏正文会作为 assistant 历史原样回传（`reply.ts toAssistantParam`），服务端对含保留特殊 token 的输入直接拒绝 → 之后每条消息都失败。状态复位也不完整：`streamReply` 只用 `void` 启动、外层只有 `try/finally` 没 catch，异常逃出去后消息可能停在 pending/streaming，输入框一直锁在「停止生成」。
3. **会话"消失"**：`db.loadSessionSummaries` 用 `getAll('sessionSummaries')` 一把读，**任意一条坏记录反序列化失败会让整个读取 reject** → 列表空 + 加载错误提示；`saveSession` 也没有任何清洗，缺 `files` 的旧/导入记录会让这条会话永远存不进去。

**修复**：
- `src/utils/specialTokens.ts`：`stripSpecialTokens`（整段兜底，覆盖 `|`/`||`/`｜`/`｜｜`/空白变体、`<|end_of_sentence|>` 等）+ `filterStreamChunk`/`flushStreamPending`（流式安全：尾部可疑前缀先缓冲，256/512 上限防不吐字）。
- 三道兜底：流式入口（`reply.ts`，只清 text 块，thinking 原文保留给续写签名）、写库/加载（`clean.ts` + `db.ts`）、显示（`view.ts`、`markdown/parse.ts` 入口）与出站（`request.ts`，assistant 文本/latest_reminder/system 清标记；用户原话只清孤立代理）。
- 列表读取：`getAll` 失败退化成按 key 逐条读，单条坏记录只丢自己；`saveSession` 写前清洗 + 容忍缺失 `files`。
- 流状态：`runReplyStream` 接 catch、`forceResetStream` 兜底复位；`streamReply` 的 finally 里也兜一次 settle，绝不把 pending/streaming 留在库里。
- 验证：`e2e-0950/dsml-test/run.mjs`（mock SSE 故意把标记切在两个事件中间）14/14 全过；完整回归 `e2e-0950/e2e.mjs` 28/28 仍全过。
