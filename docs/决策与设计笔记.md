## 二、服务端限制（实测事实，2026-11-16 用真实 Key 验证）

| 项 | 数值 |
|---|---|
| 上下文窗口 | 1,048,576 token（两个模型相同） |
| 输出上限 | 393,216 token |
| 标准模式输入实测 | 60 万字 = 167,772 token → 200 OK |
| **扩展模式输入上限** | **32,768 token（约 5.3 万字）**，超了直接 400 |

**「扩展模式」的判定看请求体里有没有扩展字段，不看用户点了什么**：

| 触发条件 | 何时出现 |
|---|---|
| `title: { enabled: true }` | 每个新会话的第一条消息 |
| `tools` 里含 `deepseek_read_url` | 旧版每个请求都声明 |
| `tools` 里含 `deepseek_web_search` | 用户开「智能搜索」 |
| `safety_check.level = high` | 用户选「内容审查 = 严格」 |

**已定方案**：四道闸门全部收进 `src/services/chat/request.ts` 的 `buildRequest()`；
估算输入超过 30,000 token 时强制标准模式（工具 / 严格审查 / 标题全部让位），
并在 `reply` 出错时降级重发一次。**已实现（0.9.28.x）。**

## 三、已经拍板的修复项

### L1 孤立代理净化（兜底）—— ✅ 已实现（0.9.28.4）
在 `buildRequest()` 里把所有 messages / system 字符串的孤立 UTF-16 代理替换成 `�`。
原因：任何一处按字符截断都可能切出半个 emoji，服务端 JSON 解析器直接 400
（实测报错：`unexpected end of hex escape`）。**已实现**：`sanitizeSurrogates` 在 `buildRequest` 里统一过一遍。

### L2 安全截断（根因）—— ✅ 已实现（0.9.28.4）
新增 `safeTruncate(text, limit)`：切割点落在代理对中间时挪一位。
替换 `compact.ts` 里的 `truncate()`、`.slice(text.length - n)`、
`store.ts` 的记录/笔记素材截取。**已实现**：`src/utils/safeText.ts`（`safeSlice` / `safeTruncate` / `safeTail`）。

### L3 预算从「字符」改成「token」—— ✅ 部分实现（0.9.28.4）
`MAX_TRANSCRIPT_CHARS` / `SEGMENT_CHARS` 等按字符的预算，改用 `estimateTextTokens()`。
理由：服务端按 token 计量，中文 / emoji / 生僻字的「字符数 ↔ token 数」差异很大，
按字符切会系统性低估。**已实现**：`compact.ts` 引入 `charsForTokens()`，预算以 token 表达再折算字符，
数值与原来等价（24,000 字符 ↔ 15,600 token）。分段切分逻辑本身没动。

## 三之二、大文件策略（2026-11-16 拍板）

**官方参考行为**：很大的文件也能传，界面显示「文件过大，模型只读了百分之多少」，
不会直接报错 —— 本质是客户端先按预算截断再发，服务端永远只收到装得下的部分。

**决定：单份文档最多占 35 万 token**（约 **53.8 万字**，350,000 ÷ 0.65）。

| 项 | 规则 |
|---|---|
| 文档预算 | 350,000 token / 份 |
| 实际可用 | `min(350k, 1,048,568 − 历史估算 − 30k 输出预留)` |
| 截断位置 | 按**段落边界**截，不按 token 硬切（顺带保证不切坏代理对，见 L2） |
| 用户提示 | 附件卡片标「已截取 62%」；回答上方一行小字说明「这份文档较长，模型读了前 62%」 |
| 不能本地读的（pdf/doc/ppt） | 无法本地截断，按体积估算提前告知风险，真超了才报错 |
| 超过预算还想读全 | 走分段摘要（方案 A：多轮总结成「文档笔记」） |

理由：90 万 token 能读全但每轮都重算，单次提问可能烧掉几块钱且很慢；
30~40 万 token 时成本可控、延迟可接受，长篇小说的前 65 万字也足够回答「讲了什么」。

**已实测（2026-11-16）**：

| 探针 | 结果 |
|---|---|
| 6.4 MB / 246 万字符 txt（服务器算 1,449,473 token） | ❌ **400**，原话 `maximum context length is 1048576 … requested 1449673` |
| `POST /anthropic/v1/messages/count_tokens` 传 document 块 | ⚠️ 返回 200 但只给 **39 token** —— 它**不统计 document 块的展开内容**，只能数字面文本 |

**结论**：
1. 服务端**不会**帮你截断，超了就是 400 —— 所以「只读了 X%」一定是**客户端行为**，DS Lite 必须自己截断。
2. 没有可靠的服务端 token 计数可用，只能本地估。实测折算比：**4.0~4.7 字节 / token**（中文），
   现有 `size / 4` 的估算偏保守（最多高估 16%），方向正确，可继续用。
3. PDF / Word 本地读不了文本，也就没法截断 —— 只能按体积预估 + 提前提示。
