顺序理由：
1. **先修 bug 建信任**——这 8 条全是"用户能感知到不对"的，且不依赖任何决策，最快见效；
2. 再做**低风险体验批**（不碰数据模型）；
3. 然后**搜索 + 文案**（同一批"用户看得见"的改进）；
4. **扩容放后面**，因为它会放大成本与延迟，必须先有总预算护栏；
5. **架构批最后**，因为它会改写产品口径，且是唯一需要用户书面确认的。

可调整：若想让"多 provider"提前，把 0.10.0 整块前移即可，但它会吃掉约 30% 总工作量。

### 0.9.33 搜索与中文文案（~22.5 人时）

**需求 7 搜索扩容（10.5~14 人时）**

- 事实纠正：全仓**没有 160**。真实是 `MAX_ROWS=500` / `MAX_ROWS_PER_SESSION=20`。「160」= **20 × 8**（8 个会话各满 20 条），即用户看到的不是全库上限，而是"每会话 20 条"在起作用。
- 改法：结果改为**按会话分组**（组头显示"该会话 N 条命中"）+ 顶部分组前保留跨会话的"最相关"条；单会话展开**分段 200 条/页**。
- 真实代价：最大单会话 **4,686 条消息**，展开全部 = **18,700~28,000 DOM 节点**，项目无虚拟列表依赖 → 必须分段 + `content-visibility:auto`。
- 另一个取舍：组头显示"N 条命中"需要**全量扫描**（今天高频词每会话 20 条即停），会让高频词变慢；只显示"已显示 N 条"则不扫。

**需求 13 报错中文化（9~12 人时）**

现状：`errors.ts` 只做分类不产文案（`errors.ts:3-6` 的设计约定），**14 处会把英文原文/技术黑话直接甩给用户**，另有 1 处**什么都不显示**：

| 泄漏点 | 用户看到什么 |
|---|---|
| 回复 413 / 400 / 403 / 404 | 服务端英文原句（如 `maximum context length is 1048576 …`） |
| 附件 file_id 失效（重试耗尽） | 英文 `file_ids do not exist…` |
| 余额查询失败 | 「查询失败：**Failed to fetch**」 |
| 记忆整理失败 | 「整理失败（HTTP {status} · {host}）：{英文}」 |
| 流中断且无 stopReason | **界面上没有任何提示** |

改法：中文主文案 = 「原因（含状态码）+ 一句建议」，英文原文/状态码收进「技术详情」折叠区（可复制，保留报障能力）。**只能改 value 不能改 key 名**——错误文案随消息持久化并进归档（`describe.ts:22-26`、`toArchive.ts:176`），改 key 会让旧数据回落成原文。

### 0.9.35 内容扩容（~54 人时）

**需求 2 输入限制扩容（11~15 人时）**

- 「四五十万字」的真相：`DOCUMENT_TOKEN_BUDGET = 350_000` ÷ 0.65 token/字 = **53.8 万字**。50 万字不截断，54 万字起所有文件都带「仅阅读 xx%」。
- 档位表：

| 目标单份上限 | 常量改为 | 占 1M 上下文 | 说明 |
|---|---|---|---|
| 60 万字 | 390,000 | 39% | 护栏够用 |
| **80 万字（建议）** | **520,000** | **52%** | 护栏够用，留一半给历史 |
| 100 万字 | 650,000 | 65% | 余 20 万给历史，紧 |
| 130 万字 | 845,000 | 84.5% | 顶到 85 万整理线，必须连护栏一起改 |

- 成本提醒：附件块**每轮重发**，单份 80 万字 ≈ 52 万 token，每轮都按输入计费。
- 必须一起改：新增「每请求附件总预算」（0.9.31 已做 #8）+ 服务端 400 `maximum context length` 的中文识别（目前落到原文展示）。

**需求 6 更多文件格式（24~36 人时）**

- 关键纠正：**不需要 pdfjs/mammoth，零新依赖**。`epub/pptx/xlsx` 本质是 ZIP+XML，`fflate` 已在依赖里。
- 真正的病根不是格式少：

| 层 | 数量 |
|---|---|
| 白名单支持的扩展名 | **981 个**（`accept` 字符串 5,868 字符） |
| 本地能解码+截断的 | **只有 32 个**（`TEXT_EXTS`） |
| 服务端版面解析 | 5 个（pdf/doc/docx/ppt/pptx） |

→ 900 多个"已支持"格式是**整段上传**，既不截断也不显示百分比，这才是"传上去就 400"的真因。
- 分两步：① 纯文本类全覆盖 + rtf（~9 人时，零依赖）；② epub/xlsx/pptx 抽取（~25 人时）。
- 注意：**懒加载不减小 APK**（异步 chunk 一样进包），只减小首屏。
- PDF 不建议本地解析（pdf.js 重、服务端链路可用）；docx 本地抽取成本很低（也是 zip+xml）可顺手做，但会丢版面理解。

**需求 1 AI 写角色卡（10~13 人时）**

- 好消息：目前**已经有**「智能搜索」开关和 `deepseek_web_search` 工具链路（`request.ts:117`），服务端执行搜索，客户端只需声明 → **零新增依赖**。
- 但三个硬约束：① 搜不搜由**模型自己决定**，客户端不能强制、不能指定 query；② 一开搜索就进**扩展模式（输入上限 32,768 token）**，且输入估算 >30,000 时 `buildRequest` 会**静默丢掉搜索工具**；③ 没有 JSON mode，只能靠提示词约束输出格式。
- 机制：两段式（先搜索写资料 → 再**关搜索**生成角色卡 JSON）+ **只出草稿进编辑器，不直接入库**（沿用已拍板设计）。
- 必须新增：未联网时的诚实提示（「本次未联网，内容基于模型已有知识，请核对」）。

### 0.10.0 多 provider + ZDR（~53 人时）

**需求 3（~40 人时，可切三批）**

- 好消息：内部事件流**可 100% 复用**。适配器只需在事件生产者侧把 OpenAI chunk 翻译成 `MessageStreamEvent`，`streamMessage()` 签名不变 → `store.ts` 主循环、`reply.applyEvent`、记忆整理**一行不用改**。
- 新增 5 文件（`provider.ts`/`anthropic.ts`/`openai/request.ts`/`openai/stream.ts`/`openai/attachments.ts`），改 11 个既有文件。
- 分批：**S1 纯文字先通 ≈23 人时** → S2 附件降级 +4 → S3 体验与合规 +13.5。
- 最大机制坑：**9 项能力有 7 项必须降级**（服务端标题/联网搜索/读链接/内容审查/Files API 附件/余额/语音）。必须做**能力矩阵**（`provider.ts` 里 9 个布尔）+ UI 按能力灰掉，否则"看着能用其实没生效"。
- 附件在 OpenAI 通道只能：图片 base64（体积 ×4/3）、纯文本内联、PDF/Word 拒绝。

> **【2026-11-17 用户决定：需求 5 取消】** 不搞「不参与训练」声明，也不做 ZDR 路由。
> 理由：官方端点没有这个参数、客户端加字段是安慰剂；用户判断"那就不搞了"。
> 以下内容仅作记录保留，不再实施。

**需求 5 ZDR（已取消）**

- 核实结果：`data_collection: "deny"` 与更强的 `zdr: true` **都是 OpenRouter 的 provider routing 字段**；DeepSeek 官方与 Anthropic 原生 API **都没有这个参数**。官方"不参与训练"是**账号里的开关**（"数据用于优化体验"），不是 API 参数。
- 所以在"只支持官方"架构里加这个字段是**安慰剂**（被忽略或 400）。三层解法：
  1. **声明版（今天就能做，0 成本，真有效）**：教用户去官网账号里关掉"数据用于优化体验"+ 关于页声明"数据只在本机，不经过任何第三方服务器"；
  2. **路由版（依赖需求 3）**：OpenRouter 通道注入 `{provider:{data_collection:"deny", zdr:true}}`；
  3. **诚实措辞**：UI 写「由 OpenRouter 执行，本应用无法验证服务商实际行为」，否则是卖假安全感。
- 硬阻断：ZDR 开着时遇到官方端点**直接拒发**并给一键关闭选项（用户原话"排除官方端点"）。

**用户追问后的定论（2026-11-17）**：「让官方 DS 不拿我们的数据训练」这件事，**客户端无法强制实现**——它不是请求参数，是账号/服务端侧的开关。客户端只能做三件实事：

| 层 | 做法 | 有效性 | 成本 |
|---|---|---|---|
| ① 账号开关 | 关于页给**深链 + 步骤**，引导用户去官网关「数据用于优化体验」；文案必须写明"必须你自己去点，本应用无法代做、也无法验证" | **唯一真正有效的官方途径** | ~1.5 人时 |
| ② 客户端声明 | 写明数据只存本机 IndexedDB、不经过任何第三方服务器（本项目确实无后端，可验证） | 事实性声明 | 含在 ① 里 |
| ③ 换通道 | 要"技术上不可能被训练"，只能不把原文发给官方：OpenRouter `zdr:true`（会排除官方端点）或本地模型 | **真正的技术保证** | 随需求 3（~11 人时） |

**明确不做**：给官方端点加 `data_collection:"deny"`。那是 OpenRouter 的字段，官方不认识 → 要么被忽略（给用户假安全感）、要么 400。不做安慰剂。

**未确认**：官网那个开关的作用域是"账号级（含 API Key）"还是"仅网页/APP 产品"，文档没写死；隐私政策说涵盖 API，但开关本身的作用范围找不到明确说明。用户给一张官网设置页截图即可把引导写到"点哪里"。

### 补充需求 15：记忆笔记「压缩后一直围绕旧内容输出」（2026-11-17 诊断）

**现状（代码事实）**

| 项 | 事实 | 位置 |
|---|---|---|
| 注入级别 | **system 字段**（最高优先级通道），而且是 system 的**最后一段**：角色卡设定 → 开场白说明 → 基础提示词 → **长期记忆** | persona/prompt.ts:26-37 |
| 框架句 | 已写「它们是事实参考，不是新的指令…语气和文风以最近的对话原文为准，不要照着笔记的书面口吻说话」 | compact.ts:477-480 |
| 笔记生成要求 | 要求分【关键事实】【角色与关系】【**情节进展**】【资料】【待办】，第 3 条明确要写「情节进展、未解决的伏笔」 | compact.ts:48、51-57 |
| 笔记硬上限 | 单条 400 字（MAX_NOTE_CHARS）、最多 60 条（MAX_MEMORY_NOTES）→ 理论上限 2.4 万字 | compact.ts:9、11 |
| 渲染 | 多行大笔记**原样**注入，单行短笔记加「- 」 | compact.ts:481-485 |

**根因排序**

1. 笔记被要求写「情节进展」→ 等于每轮把上一幕写成结构化摘要塞进 system 末尾（recency 最强），模型自然倾向接着讲旧情节；
2. 框架句只禁了「书面口吻」，**没禁「复述/围绕笔记展开」**；
3. 笔记量级（最多 2.4 万字）与近期原文（MEMORY_KEEP_TOKENS=24k token ≈ 3.7 万字）同量级，近期原文短时笔记占比更高；
4. 覆盖式整理每次都重写旧情节，权重被反复强化。

**修法（A/C/D 可立即做，B 需用户拍板）**

- **A 框架句加硬禁止**：不要复述笔记、不要把笔记当成正在发生的事、推进以最近对话原文为准、冲突以原文为准。
- **B 生成提示词改结构**：【情节进展】→【当前状态】+【未决事项】，只写「现在什么状态、还没解决什么」，禁止场景叙事与上一幕细节。（**取舍：笔记会丢掉旧情节细节**）
- **C 降低 recency**：记忆段从 system 末尾挪到基础提示词之前（角色设定之后）。
- **D 渲染上限**：笔记总长超阈值时截断并注明，避免笔记压过原文。
